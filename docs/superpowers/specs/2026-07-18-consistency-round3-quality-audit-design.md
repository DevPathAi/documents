## 1. 배경과 목표

42번(2차 점검, 7-02) 이후 약 2주간 대량의 구현이 머지되었다: 에러 envelope 표준화(5개 svc), Tier-2 웹 실API 전환, 마이페이지 P1~P4, 설정/동의, Google OAuth, 베타 게이팅(C1/C2a/C2b), 결제 마스터 spec, 웹 이미지(WS-B). 과거 두 차례의 점검이 보여주듯 **구현 속도가 문서 갱신 속도를 앞지르므로**, 실배포(WS-D) 착수 전에 3차 점검이 필요하다.

이번 점검은 기존 문서 정합성 축에 더해 **코드 품질 축(코드 규칙 준수·TDD 적합성)을 신설**하고, 발견된 문제를 **안전·소형 리팩토링**으로 실제 해소하는 것까지를 범위로 한다.

**목표**:
1. 코드 ↔ 문서 불일치를 전수 식별하고 해소한다 (코드가 진실 원칙).
2. 코드 규칙(09·10·12번, 각 레포 CLAUDE.md) 위반과 레포 위생 문제를 식별·수정한다.
3. TDD 갭(구현 대비 테스트 부재·부실)을 식별하고 우선순위 높은 갭에 테스트를 보강한다.
4. 동작 불변이 보장되는 안전·소형 리팩토링을 실행한다. 대형 구조 변경은 기록만 한다.

**성공 기준**:
- 46번 보고서가 42번 형식(결론→기준→회귀체크→불일치 P0/P1/P2→코드 관찰)으로 작성·머지됨.
- 47번 실행계획의 P0·P1 Task가 전부 PR로 실행·머지됨 (P2는 명시적 이월 가능).
- 모든 코드 변경 PR은 해당 레포 테스트 통과 + CI 녹색 확인 후 머지됨.
- 리팩토링 전후 동작 변경 없음 (기존 테스트 + 보강 테스트로 방어).

## 2. 범위·기준선

### 2.1 대상 레포

- **문서 축**: `documents` 전체(01~45 + Home/README) + 각 레포 README·CLAUDE.md + `.github` 조직 프로필 + `workflow-guide` 연동 영향.
- **코드 축**(구조·규칙·TDD): 코드 보유 12개 레포 — devpath-{platform,learning,community,sandbox,ai,lcs,notification}-svc(7종) + devpath-gateway + devpath-frontend + devpath-shared + devpath-svc-template + devpath-gitops(매니페스트).
- **참고 대상**(불일치 발견 시만 기록): prototype, storyboard, templates, workflow-dashboard, workflow-guide, devpath-home-page, devpath-landing-page.

### 2.2 기준 ref

- 각 레포 **`git fetch` 선행 후 `origin/develop`** (없으면 기본 브랜치). 점검 시작 시점에 레포별 SHA를 고정해 46번 §2에 표로 기록한다 (42번 §2.1 형식).
- 읽기는 `git show`/`git ls-tree`/`git grep <기준ref>` 우선 — **워킹트리를 점검 기준으로 삼지 않는다**.

### 2.3 워킹트리 dirty 처리

- 점검 기준에서 제외하되 **위생 항목으로 별도 기록**한다. 2026-07-18 현재 확인분:
  - 대부분 레포의 `.omc/`(oh-my-claudecode 세션 상태) untracked 오염. community-svc는 `.omc/state/*`가 **과거 커밋에 포함**되어 있음.
  - documents 미커밋 3파일: `.tier1-baseline.md`, `docs/superpowers/plans/2026-06-24-landing-validation-test-plan.md`, `docs/superpowers/specs/2026-06-24-office-hours-landing-validation-design.md`.
- 실행 단계에서 정리: `.omc/`를 각 레포 `.gitignore`에 추가, community-svc 추적분 `git rm --cached`, documents 방치 파일은 커밋 또는 폐기 판단.

### 2.4 제외

`*.zip`, `*.pdf`, `node_modules/`, `build/`, `.gstack/`, 빌드 산출물 (42번 동일).

### 3.1 회귀 체크

43번 실행계획의 이행 현황을 42번 §3 형식으로 재확인한다 (✅/⚠️/❌/➖). 42번 잔여 ⚠️(P0-5 웹 렌더링 미검증)와 메모리상 OPEN 항목(sandbox-svc #18, .github #6)의 현재 상태도 확인한다.

### 3.2 수행 방식

- **병렬 서브에이전트**로 레포별·축별 분담, 컨트롤러가 교차 종합. 42→43 패턴의 3단계 순차: ①전체 점검 → ②전역 종합·실행계획 → ③Task별 실행.
- 서브에이전트는 **읽기 전용·보고만** (scope lock): "이 점검만 수행, 끝나면 보고 후 정지, 수정 금지, 모든 명령에 절대경로 또는 `git -C <절대경로>` 사용".
- 산출: 축별/레포별 원자료를 `docs/superpowers/reports/2026-07-18-consistency-round3-*.md`로 남기고, 46번 보고서가 이를 종합·인용한다.

## 4. 실행 단계 (계획 → 리팩토링)

### 4.1 실행계획 문서

`47_품질_리팩토링_실행계획서.md` — 발견 항목을 P0(사실 왜곡·규칙 위반 심각)/P1(불일치·주요 갭)/P2(경미)로 분류하고, Task 단위로 **파일 경로·수정 내용·검증 명령을 직접 명세**한다 (서브에이전트가 스스로 범위를 해석하지 않도록).

### 4.2 실행 플로우

- 레포별 `develop`에서 분기: 문서 수정 `docs/*`, 위생·규칙 수정 `chore/*`, 리팩토링 `refactor/*`, 테스트 보강 `test/*`.
- 브랜치 → PR → **CI 녹색 확인 후** 머지 (merge commit 기본). `main`·`develop` 직접 푸시 금지.
- shared 컨트랙트 변경이 생기면 develop 수동 발행(`gh workflow run publish.yml --ref develop`) 절차를 따른다.

### 4.3 리팩토링 안전 기준

- **동작 불변 보장**: 변경 대상 코드에 테스트가 없으면 **먼저 현재 동작을 고정하는 테스트를 작성**(실패 확인이 가능한 신규 검증은 실패 확인 후 구현 — TDD)하고, 통과 상태에서 리팩토링한다.
- 허용: 데드코드 제거, 중복 제거, 규칙 위반 수정(네이밍·envelope·설정), 명명 정리, 누락 테스트 보강, .gitignore·레포 위생.
- 금지(기록만): 모듈·패키지 경계 재조정, 공통 로직 shared 이관, API 시그니처 변경 등 대형 구조 변경 → 46번 §관찰에 기록.

### 4.4 검증

- PR마다: 해당 레포 테스트 로컬 실행 통과 + CI 녹색 + 리뷰 체크리스트(12번) 셀프 점검.
- 컨트롤러 직접 검증: 서브에이전트 완료 보고 무신뢰 — `git log` 커밋 범위, 파일 구조, 테스트 실행 결과를 직접 확인하고, 인접 레포에 낯선 브랜치·커밋이 없는지 스팟체크.
- 테스트 실패 시: 근본 원인 규명 우선(systematic-debugging), 증상 땜질 금지. Testcontainers 'too many clients' flake는 기존 해법(hikari maximum-pool-size 하향) 참조.

### 4.5 에러 처리

- 서브에이전트 명세 부족 시 `NEEDS_CONTEXT` 정지 → 컨트롤러가 직접 확인 후 재위임.
- Windows 서브에이전트 불안정(완료 보고·resume 무신뢰): resume 실패 시 신규 dispatch로 전환.
